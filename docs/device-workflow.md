# 设备接入与固件迁移全流程

记录一台 7.5 寸黑白红墨水屏价签从到手、排障、定位固件 bug，到建立 CI 和验证 DFU 的完整过程。所有结论都有对应的实测或代码依据。

## 阶段一 通过蓝牙识别设备

自定义服务：

```
服务    62750001-d828-918d-fb46-b6c11c675aec
命令    62750002-d828-918d-fb46-b6c11c675aec   notify, write, write-without-response
版本    62750003-d828-918d-fb46-b6c11c675aec   read
```

订阅命令特征值后，固件立刻推送 13 字节的 `epd_config_t`，字节顺序与结构体一致，前七个是引脚，第八个是型号，后面依次是唤醒脚、LED、EN、显示模式、周起始。

版本特征值读出来是 0x20。这里第一次发现版本对不上：本地仓库当时是 0x1a，说明设备跑的不是主线。

随后确认 `0000fe59` 服务存在，特征值 `8ec90003` 可写可指示，说明这是 nRF52 平台加无按键 DFU。

## 阶段二 显示异常

### 现象

- 日历和时钟界面基本正常，但有横向浅带
- 纯黑、纯白正常
- 纯红发灰
- 三色图片整屏碎成竖条纹，红色完全不见

### 排查

用 C 端脚本直接走 BLE 写 RAM，绕过网页。第一版用上游的老协议 `0x30`，失败，因为 fork 重写了传输路径。

读 fork 源码后改用块协议 `0x31`：

```
[0x31][块号低][块号高][总数低][总数高][cfg][载荷][CRC低][CRC高]
```

CRC 是 CRC16/X25，多项式 0x8408，初值 0xFFFF，覆盖载荷。cfg 低半字节 0x0F 表示黑白层，0x00 表示红色层，高半字节 0x00 表示每层第一块。

传输带状态查询 `0x32`，返回 7 字节头加位图，可以用来补发丢失的块。

实测两层都是 204/204 块全部到达，排除丢包。

### 根因

`EPD/UC81xx.c` 的 `UC81xx_Write_Ram` 在每层第一块只切换 DTM 命令，没有重设 RAM 窗口：

```c
if (begin) {
    if (epd->color == BWR)
        EPD_WriteCmd(black ? UC81xx_DTM1 : UC81xx_DTM2);
    else
        EPD_WriteCmd(UC81xx_DTM2);
}
```

黑白层写满整帧后地址计数器不在 0,0，红层从错误位置继续写。单色图看不出来，因为整帧同色。

上游 tsl0922 在对应位置有一行 `UC81xx_SetWindow(0, 0, width, height)`，fork 删掉了。

### 验证

在每层传输前手动发一条 `0x90` 全屏窗口命令：

```
03 90
04 00 00 03 1F 00 00 01 DF 00
```

再发纯红图片，整屏正常变红。根因确认。

### 修复

提交 `7a8a51e`，在 `UC81xx_Write_Ram` 和 `UC81xx_Write_Ram_Native` 的 begin 分支里补上 `_setPartialRamArea(0, 0, width, height)`。已作为 PR #4 提交到 YCD12。

## 阶段三 供电问题

屏在纯白下完全干净，但内容一多就出现从上到下的渐变，且等多久都不恢复。

为了判断是面板还是扫描时序，把 PSR 的 D3 位从 1 改成 0，反转栅极扫描方向：

- `PSR 0x0F`，渐变在下
- `PSR 0x07`，渐变在上

渐变跟着扫描方向走，说明像素本身没坏，是刷新过程中驱动能力逐渐衰减。

对照设备电压读数 2.5V 到 2.6V。CR2450 并联的持续放电能力只有几毫安，而 7.5 寸屏刷新时升压电路的输入电流是几十毫安，电池内阻导致电压塌陷。

重新安装电池后电压回到 2.7V，日历模式刷新完全正常。结论确认：面板和驱动没问题，是供电余量不足。

## 阶段四 仓库与 CI

### fork 限制

GitHub 规定同一仓库网络只能有一个 fork。账号下已有 tsl0922 的 fork，所以无法直接 fork YCD12。最终方案：

- 删除旧的纯镜像 fork
- 直接 fork YCD12，得到完整历史，服务端复制，不用上传

### 推送大文件失败

仓库带完整 SDK 约 60MB，推送反复返回 HTTP 408。原因不是代理，而是单次请求体过大。改用 GitHub API 逐文件提交，或者先剔除 SDK 再推。

后者的做法：

- 排除 `SDK/`、`tools/bin/`、`docs/datasheets/`
- 体积从 52MB 降到 2.28MB
- 一次推送成功

### CI

`.github/workflows/firmware.yml`：

1. Ubuntu 环境，`apt install make gcc-arm-none-eabi`
2. `actions/setup-python@v5` 指定 3.10，因为 nrfutil 6.1.7 不支持 3.12
3. 把 `Makefile.posix` 复制进 SDK 的工具链目录，指定 `/usr/bin/` 为工具链根
4. `cp Makefile.nRF52 Makefile` 后 `make`，SDK 的构建规则依赖名为 `Makefile` 的文件
5. `arm-none-eabi-size` 输出体积
6. `nrfutil pkg generate` 打包，`--hw-version 52 --sd-req 0x126 --sd-id 0x126`
7. 上传 hex 和 zip 两个产物

分支约定：

| 分支 | 内容 | 版本 |
|---|---|---|
| `fix/ram-window` | 只含窗口修复，作为 PR #4 的头 | 0x20 |
| `build/step1` | fork 加修复加构建适配 | 0x21 |
| `mainline` | tsl0922 主线加构建适配 | 0x22 |

## 阶段五 体积问题

### 应用区只有 64KB

内存布局固定：

| 地址 | 内容 |
|---|---|
| 0x00000 | MBR |
| 0x01000 | S112，到 0x18FFF |
| 0x19000 | 应用，到 0x28FFF |
| 0x29000 | DFU 引导 |

但 Keil 工程和 SDK 的链接脚本都写的是 `0x19000 + 0x17000`，允许长到 0x30000。这个配置只适用于没有引导的场景，用它会静默覆盖引导。

两个分支都改用限制在 `0x10000` 的链接脚本，超界直接链接失败。

### 主线超 940 字节

初次构建 66792 字节。原因是 GUI 里两处双精度乘法：

```c
y + 4.5 * cS + 1
y + 13.5 * cS + 3
```

Cortex-M4 没有硬件双精度，软浮点库被整个链接进来。改成整数：

```c
y + (9 * cS) / 2 + 1
y + (27 * cS) / 2 + 3
```

体积降到 65176 字节，装进 64KB。

### fork 超 5468 字节

除了同样的双精度，fork 还把电压改成 `float` 并用 `%.1fV` 打印，多拉进浮点格式化和浮点运算库。处理：

- 开 `-flto`
- 双精度改整数
- `EPD_ReadVoltage` 改为返回整数毫伏，`DrawBattery` 用整数算电量，打印改 `%d.%dV`
- 去掉异常展开表、`NDEBUG`、移除未使用的日志与 RTT 源文件

最终 65044 字节。

### 两个分支的体积

| 分支 | text | data | 合计 | 余量 |
|---|---|---|---|---|
| build/step1 | 64504 | 540 | 65044 | 492 |
| mainline | 64860 | 316 | 65176 | 360 |

## 阶段六 DFU 引导验证

在刷任何自制固件之前，先确认引导是否还在。

做法：对 `8ec90003` 先开启指示，再写入 `0x01`：

```python
await client.start_notify(BUTTONLESS, cb)
await client.write_gatt_char(BUTTONLESS, b"\x01", response=True)
```

返回 `20 01 01`，表示进入引导成功。设备复位后广播为：

```
DfuTarg   ED:F1:7F:A0:E9:0C
  控制点 8ec90001  True
  数据包 8ec90002  True
```

引导存活，安全 DFU 服务完整。这一步只写 GPREGRET 和复位，不写 flash，失败也不会变砖。
